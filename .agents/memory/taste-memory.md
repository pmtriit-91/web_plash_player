# Taste Memory Protocol

Use to store the enduring aesthetic taste of the project or owner.

Taste is a warm `convention` record with `user-confirmed` authority. It must cite a
durable project evidence file; raw conversation is never stored as evidence.

## When to update

Update when the user clearly confirms a long-term preference, for example:

- Dislikes overly mechanical UI.
- Prefers cinematic/luxury/premium.
- Prefers layouts with breathing space.
- Dislikes generic card grids.
- Wants an Apple/Tesla/Porsche feel.
- Wants directed motion, not simple fade-ups.
- Taste memory only serves as a guide for preference/aesthetics, not a mandatory rule that can override the user's current requests or the actual constraints of the project.

## Do not store

- Temporary opinions on a small screen.
- Speculation.
- Preferences not confirmed by the user.

Use the Context Record schema and keep the summary compact: preference, anti-pattern,
applicable surface, and any confirmed example.
